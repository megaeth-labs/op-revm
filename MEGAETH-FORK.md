# MegaETH fork of op-revm

This repository is MegaETH's fork of the `op-revm` crate, the OP Stack variant of [revm](https://github.com/bluealloy/revm).
`op-revm` has no standalone upstream repository: it lives in `rust/op-revm` of the [OP monorepo](https://github.com/ethereum-optimism/optimism).
The fork starts from a snapshot of that directory and carries MegaETH's commits on top.
The crate name and version stay `op-revm 20.0.0`; consumers switch to the fork through a `[patch]` entry pinned to a tag or commit, never through a renamed dependency.

## Why a fork

MegaETH's execution engine runs on the [MegaETH fork of revm](https://github.com/megaeth-labs/revm), which carries the revm 43 gas core on top of revm 40.0.3.
That gas core changed the shape of three `Handler` methods that `OpHandler` overrides, and the monorepo copy of `op-revm` pins an older revm with no port.
The crates.io package `op-revm 20.0.0` is a different package under the same name and version (published from an older monorepo commit, depends on revm 38, maps `INTEROP` to `PRAGUE`) and is not compatible either.
This fork is the monorepo copy plus that port, and nothing else: MegaETH logic stays in `mega-evm`.

## Branch model

| Ref | Content | Who writes |
|---|---|---|
| `main` | The snapshot commit, then MegaETH commits on top, linear. `git log <snapshot>..main` is the whole fork diff. | PRs, CI green required |
| `v20.0.0-mega.N` | Fork releases, always on `main`. The only tags in this repository. | An admin, by hand |

## Rules

1. **Public API is a superset of the snapshot.**
   Do not change existing signatures, remove items, add trait methods without a default body, or rename features.
   `mega-evm`, `mega-reth` and `alloy-op-evm` are compiled against this fork; a change that must break the API says so in the PR and lands together with the consumer change.
2. **Only what the revm fork requires.**
   Upstream code changes where the MegaETH fork of revm changed a `Handler` method that `OpHandler` overrides, and nowhere else.
   An OP behaviour change belongs upstream; a MegaETH decision belongs in `mega-evm`.
3. **Cargo versions never change.**
   `[patch]` only applies when the patched version satisfies the consumer's requirement.
   Releases are identified by git tags only.
4. **Commit prefix `mega:`, one commit per topic; snapshot commits start with `Mirror op-revm@`.**
   Every upstream file the fork edits has a row in the "Upstream touch points" table below.
5. **`no_std` is mandatory.**
   The crate must keep building for `riscv32imac-unknown-none-elf` and `riscv64imac-unknown-none-elf` with `--no-default-features`.
6. **The toolchain is pinned.**
   `rust-toolchain.toml` names the compiler this repository is checked with, the same pin as the revm fork.
   Upstream floats on `stable`; the fork carries upstream code it does not edit, so a floating toolchain would fail CI on lints in code the fork must not touch.
7. **The revm fork commit is pinned in one place.**
   `Cargo.toml` keeps the upstream requirement `revm = "40.0.3"`; `.cargo/config.toml` (introduced together with the port) patches `revm` to one commit of the MegaETH fork, and that is the commit this crate is built and tested against.
   A consumer redirects `revm` (all twelve fork crates) to that commit or a later compatible one, and `op-revm` to a tag of this repository.
   Consumers do not inherit the config patch.

## Upstream touch points

Files that both upstream and the fork edit.
Keep this list current; it is the set of changes a new snapshot must carry over.

| File | Fork change | Rule for the next snapshot |
|---|---|---|
| `src/fast_lz.rs`, `src/handler.rs`, `src/l1block.rs`, `src/precompiles.rs` | six binary-operator line breaks moved to the line start | run `cargo fmt` on the pinned stable toolchain; `binop_separator = "Back"` is nightly-only |
| `Cargo.toml` | `workspace = true` inheritances flattened to concrete values | regenerated by `scripts/mega/flatten-manifest.py` inside `scripts/mega/mirror.sh`; never edit by hand |

`rustfmt.toml` is a copy of the monorepo's `rust/rustfmt.toml` so `cargo fmt --check` keeps the OP style; it is fork-owned and not a touch point.
`scripts/mega/check-touch-points.sh <base> <head>` lists any edited upstream file that lacks a row.

## Consumer wiring

A consumer redirects `op-revm` at the source it declares it from, pinned to a tag of this repository, and redirects `revm` (all twelve fork crates) to the MegaETH fork of revm at the commit named in `.cargo/config.toml` or a later compatible one:

```toml
[patch."https://github.com/ethereum-optimism/optimism"]
# mega-reth declares op-revm from the OP monorepo
op-revm = { git = "https://github.com/megaeth-labs/op-revm", tag = "v20.0.0-mega.1" }

[patch.crates-io]
# a consumer that declares the crates.io package instead
op-revm = { git = "https://github.com/megaeth-labs/op-revm", tag = "v20.0.0-mega.1" }
# plus the twelve revm crates, see MEGAETH-FORK.md of megaeth-labs/revm
```

`Cargo.lock` records the resolved source; commit it, so a workspace that loses the patch fails to build instead of silently resolving the monorepo copy.

## Moving to a new upstream snapshot

1. Produce the snapshot tree from a monorepo clone at the new revision: `scripts/mega/mirror.sh <clone> <rev> <dir>`.
2. Replace the crate files in a working tree with that tree (everything except the fork-owned files listed in `scripts/mega/check-touch-points.sh`) and commit it as `Mirror op-revm@<short> from ethereum-optimism/optimism`, with the full commit id, date and crate version in the body.
   Update `scripts/mega/base.txt`, the baseline table above and `PROVENANCE.md` in the same commit.
3. Re-apply every touch-point row on top, one `mega:` commit each, following the rules in the table.
4. Before opening the PR, run `scripts/mega/check-mirror.sh <clone>` and `scripts/mega/check-touch-points.sh <snapshot> HEAD`; paste both results into the PR.
5. Tag a release.

## Following a new revm fork commit

Bump the `rev` in `.cargo/config.toml`, fix whatever the new `Handler` shapes require in `src/handler.rs` (rule 2), update the touch-point row, and tag a release.

## Release procedure

Every release is a commit on `main` with green `ci success`.
An admin tags it by hand and pushes the tag:

```bash
git tag -a v20.0.0-mega.N -m "v20.0.0-mega.N" <commit>
git push origin refs/tags/v20.0.0-mega.N
```

The tag name is `v<crate version>-mega.<N>`; the crate version never changes, so `N` only counts up.
Tags cannot be moved or deleted (ruleset); a wrong tag is superseded by the next number.

## Repository settings (admin)

- `main` is protected: pull requests only, one approval, squash merge only, required check `ci success`.
- Force pushes are banned on every branch; a wrong branch is replaced, not rewritten.
- Release tags cannot be updated or deleted.
- No secrets, apps or bots are needed.

## CI

`ci.yml` runs on every pull request and on pushes to `main`: tests (default and all features), `no_std` checks on both riscv targets, clippy with `-Dwarnings`, and fmt, all on the pinned toolchain; `ci success` gates the merge.

Local equivalents: `cargo fmt --all --check`, `cargo clippy --all-targets --all-features` with `RUSTFLAGS=-Dwarnings`, `cargo nextest run` and `cargo nextest run --all-features`, `cargo check --no-default-features --target riscv32imac-unknown-none-elf` (and riscv64).
Manual checks for a mirror PR: `scripts/mega/check-mirror.sh <monorepo-clone>` and `scripts/mega/check-touch-points.sh <snapshot> HEAD`.
